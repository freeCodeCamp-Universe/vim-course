# Lesson authoring reference

Rules and conventions for writing lesson files. For the command surface the
terminal simulates, see [`commands.md`](commands.md).

## Lesson file structure

Each lesson is `src/curriculum/<NN>-<slug>/<id>.md`.

**Frontmatter**

| Field    | Notes                                                                                    |
| -------- | ---------------------------------------------------------------------------------------- |
| `id`     | Matches the filename. Generated by `scripts/scaffold-curriculum.mjs`; never hand-edited. |
| `module` | Module number. Cross-checked against `ordering.ts` at load time.                         |
| `title`  | Shown in the UI.                                                                         |
| `type`   | `learn`, `practice`, `intro`, or `review`. Does not affect validation.                   |

## Author notes

Every lesson includes a non-rendered `# --author-notes--` section with these subsections:

```markdown
# --author-notes--

## CAG

**Concept:**

- What the lesson introduces or reinforces.

**Activity:** What the learner does.

**Goal:** What the learner can do after the lesson.

## Notes

Author context, decisions, review recaps, or other implementation notes.
```

Use `Concept: None new.`, `Activity: Review.`, and `Goal: Review.` when a review has no more specific CAG. Keep notes outside `## CAG`. The curriculum sync script publishes only the Concept, Activity, and Goal labels in that subsection to the master curriculum document.

To sync the document from the lesson files and `ordering.ts`, run `pnpm sync-curriculum-doc -- --source=curriculum`. To make the curriculum document authoritative and update lesson metadata, C/A/G author notes, lesson order, and WIP status, run `pnpm sync-curriculum-doc -- --source=doc`. Add `--check` to either command to validate without writing.

**Section markers**

| Marker               | Purpose                                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `# --instructions--` | Prose shown to the learner.                                                                          |
| `# --files--`        | Seed files: one `## <filename>` heading + code fence per file. Required on every interactive lesson. |
| `# --config--`       | JSON config block. Its absence makes a lesson prose-only (no terminal, no checklist).                |
| `# --expected--`     | Target end-state bodies, one `## <filename>` per file, read by `equalsExpected` tests.               |

## Tab groups in instructions

Prose lessons (those with no `# --config--`) can embed tabbed file viewers inside `# --instructions--` using `:::tabs` / `:::` fenced regions. Each tab group renders as a tab bar with file-name tabs and a preformatted content panel.

A page may contain multiple tab groups interleaved with normal markdown.

**Syntax**

````markdown
# --instructions--

## Motion Commands

These commands move the cursor without changing text.

:::tabs

### motions.vim

```vim
h j k l      " left, down, up, right
w b e        " word forward, back, end
```

### operators.vim

```vim
d  " delete
c  " change
y  " yank
```

:::

## Ex Commands

Run these from command mode.

:::tabs

### basics.ex

```vim
:w   " write
:q   " quit
```

:::
````

**Rules**

- The heading level inside `:::tabs` is flexible (`#` through `######`). Pick
  whatever level fits the surrounding document outline; the parser treats it as
  a tab label, not a document heading.
- Each heading must be followed by a fenced code block. The language tag on the
  fence is optional.
- A `:::tabs` block must contain at least one tab entry.
- `:::tabs` blocks must be closed with a matching `:::` on its own line.

### Showing the copy button on a code fence

Fenced code blocks do not show a copy-to-clipboard button by default. To show
one on a specific block, add `copy` to the info string after the language:

````markdown
```md copy
This block has a copy button.
```
````

The language tag (`md`, `js`, etc.) is preserved as usual. `copy` can appear
without a language: ` ``` copy ` is valid.

**Rendering**

The loader parses `:::tabs` regions into structured `InstructionSegment[]` data
(`src/curriculum/tabBlocks.ts`). The view renders each tab group with the
`TabGroup` component (`src/components/TabGroup/TabGroup.tsx`), which provides
keyboard navigation (arrow keys, Home, End) and proper ARIA `tablist` /
`tabpanel` roles.

## Config block

Config fences must be labeled `json`. The loader accepts comments and trailing
commas in these blocks while parsing them as JSON.

```json
{
  "start": "shell" | "splash" | "file" | "explore" | "animation",
  "unsupportedMessage": "{sequence} is not supported in this lesson",
  "completionScene": "<scene-id>",
  "open": "<filename>",
  "cursor": [line, column],
  "scene": "<scene-id>",
  "allowedCommands": ["vim", ":w", "i", "..."],
  "disallowedCommands": [":q"],
  "commandLimits": { "dd": 3, "dw": { "times": 2, "maxCount": 1 } },
  "checklist": [{ "label": "...", "hint": "...", "test": { ... } }]
}
```

| Property             | Notes                                                                                                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start`              | `"shell"` = bare terminal; `"splash"` = Vim open, no file; `"file"` = file open (requires `open`); `"explore"` = netrw; `"animation"` = animated screen (requires `scene`). |
| `unsupportedMessage` | Optional full unsupported-command message template. Use `{sequence}` for the command and `{mode}` for the mode-specific variant.                                            |
| `open`               | Required when `start` is `"file"`. Required when `--files--` seeds more than one file. The _starting_ buffer only.                                                          |
| `cursor`             | Starting cursor position `[line, column]`, 1-based.                                                                                                                         |
| `scene`              | Required with `start: "animation"`, forbidden otherwise. Names a registered scene (e.g. `"campfire"`).                                                                      |
| `completionScene`    | Optional. Names a registered scene to show once, when every checklist item passes. Dismissing it returns to the configured `open` file.                                     |
| `allowedCommands`    | Optional. Commands not in this list are no-ops. See [below](#allowedcommands-gating).                                                                                       |
| `disallowedCommands` | Optional. Everything runs except these commands. See [below](#disallowedcommands).                                                                                          |
| `commandLimits`      | Optional. Per-command invocation caps, layered on top. See [below](#commandlimits).                                                                                         |

## Start modes

| Mode          | What opens                                                                | `open`                                                              |
| ------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `"file"`      | The named file, in normal mode                                            | Required; also required when `# --files--` seeds more than one file |
| `"explore"`   | The netrw listing                                                         | Optional — highlights the named entry, defaults to the first        |
| `"shell"`     | The shell prompt, before Vim launches                                     | **Must be omitted** — the loader throws if present                  |
| `"splash"`    | Vim's startup screen over an empty unnamed buffer                         | **Must be omitted** — the loader throws if present                  |
| `"animation"` | A looping animated scene; any key dismisses it and returns to normal mode | **Must be omitted** — the loader throws if present                  |

All of `"shell"`, `"splash"`, and `"animation"` seed `# --files--`, so `:e <path>` and `:Explore` reach those files. Only `open` is inert.

**Splash is a display flag, not a mode.** Every normal-mode command works under the splash screen, `allowedCommands` filtering included. The first keystroke that edits the buffer or loads another file clears it; commands that change nothing (`:` then `Esc`, a motion) leave it up. Because a bare `vim` names no file, `:w` and `:wq` report `E32: No file name` until an `:e <path>` is run. Build any save step after that open.

**Use `"shell"` when the lesson teaches the launch itself** (`vim <file>`, bare `vim` for splash). Use `"file"` when the session is already underway and the launch is not the point.

**Use `"animation"` for visual-interest screens.** The terminal shows a looping animation from a registered scene until the learner presses any key. The buffer is left intact underneath, so dismissal restores the editing surface. Requires `scene` in config naming a registered scene id (see `src/animation/scenes.ts` for the registry). The animation respects `prefers-reduced-motion` by rendering frame 0 statically and pauses when the tab is hidden.

### Creating an animated screen

Add a pure `SceneFn` to `src/animation/scenes.ts`, then register it with a
unique scene id, frame period, and frame rate:

```ts
const EXAMPLE_PERIOD = 2;

function exampleScene(frame: number, rows: number, cols: number): string[] {
  const border = frame % EXAMPLE_PERIOD === 0 ? '* . * . *' : '. * . * .';
  return normalizeFrame(
    [
      center(border, cols),
      '',
      center('Example animated screen', cols),
      '',
      center('Press any key to continue', cols),
      center(border, cols),
    ],
    rows,
    cols
  );
}

scenes.set('example-screen', {
  fn: exampleScene,
  period: EXAMPLE_PERIOD,
  fps: 2,
});
```

Use it as a lesson's start screen by setting `start` to `"animation"` and
referencing the registered id with `scene`. Do not declare `open` for this
start mode:

```json
{
  "start": "animation",
  "scene": "example-screen"
}
```

To show a scene after completion instead, keep the normal `"file"` start
configuration and set `completionScene`:

```json
{
  "start": "file",
  "open": "study.md",
  "completionScene": "example-screen"
}
```

The completion scene is shown once when every checklist item passes. Pressing
any key dismisses it and reopens the configured `open` file.

**There is no validation mode.** A lesson does not declare one, and frontmatter `type` decides nothing. Every checklist item carries its own `test`, is judged on its own, and owns its own checkmark, so one file's requirement never gates another's. There is no lesson-wide comparison.

A single test may assert both what the learner _did_ and what is _true now_. That's the point of one shape rather than two modes. It's how a lesson says "you used `x`" **and** "`return-key.md` now reads this way" **and** "`enter-key.md` is still exactly as seeded" in one checklist.

Checks run live as the learner works. **Go to next** is never disabled. Pressing it on an unfinished lesson marks open items and explains what is missing.

## Checklist items

Structure: `{ "label": "...", "hint": "...", "attemptsBeforeHint": N, "targetLine": "...", "evaluateWhen": { ... }, "test": { ... } }`. `hint`, `attemptsBeforeHint`, `targetLine`, and `evaluateWhen` are optional.

**Label style** Imperative, names the completed action, ends with a period:

- `"Open \`about-vim.md\`."`
- `"Return to normal mode."`
- `"Save the file and quit."`

**Hint style** Revealed one at a time when the learner finishes a failed attempt. Per-step, imperative. Starts with `"You should..."` or `"You can..."`. Include a reminder to press `Enter` for commands that need it:

- `"You should press \`Esc\` to return to normal mode."`
- `"You should type \`:w\` and press \`Enter\`."`
- `"You can use \`:wq\` to save and quit."`

**`hintOnAdvance`** When `true`, the item's hint is shown even when the checklist just advanced to it (the previous item completed on the same keystroke). Normally hints are suppressed on advance because the keystroke was a success for the prior item, not a miss for the new one. Use this on a trailing content-equality test that always co-fires with its predecessor (e.g. a save test), so the learner sees the hint immediately when the content is wrong. Requires `hint`.

**`attemptsBeforeHint`** A positive integer. Suppresses the hint until the learner has attempted and failed this many times. Without this field, hints show on the first test failure (default behavior). Use this on puzzle lessons where you want learners to struggle through several attempts before offering help. Requires `targetLine` to identify which line in the file should trigger attempt counting. See [`capstone.md`](capstone.md) for design rationale and examples.

**`targetLine`** A string that identifies the line in the target file that should trigger attempt counting. Supports plain substring (e.g., `"Key 1:"`) or regex (e.g., `"/Key\\s*1\\s*:/i"`) using the same `"/pattern/flags"` convention as `contains`. This field is required when using `attemptsBeforeHint` — it lets the system distinguish between edits to different lines (e.g., "Key 1:" vs. "Key 2:") and count attempts only on the relevant line. See [`capstone.md`](capstone.md) for examples.

**`evaluateWhen`** Defers evaluation of the item until a condition is met. When the condition is not satisfied, the item stays in its current state and a failed attempt does not reveal its hint. Use `fileOpen` for `start: 'shell'` lessons whose checklist items require a specific active buffer, or `fileChanged` when the item should become eligible after that file has been edited or written, including through `:cdo`. The `absent` condition gates evaluation on placeholder removal.

Currently supported conditions:

| Field         | Meaning                                                                                                                                                                                               |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fileOpen`    | The named file must be the active buffer before evaluation runs.                                                                                                                                      |
| `fileChanged` | The named file or files must have been edited or written before evaluation runs.                                                                                                                      |
| `absent`      | A string or array of strings. Each must be absent from the file named in `fileChanged` before evaluation runs. Combines with `fileChanged` via AND. Use this to gate the item on placeholder removal. |
| `register`    | The unnamed register must satisfy the nested register predicate before evaluation runs.                                                                                                               |

```json
{
  "label": "Finish the last sentence.",
  "hint": "You should replace the blank with the given phrase.",
  "evaluateWhen": { "fileOpen": "vim-notes.md" },
  "test": { "file": "vim-notes.md", "contains": ["more than two million times."] }
}
```

Without `evaluateWhen`, the hint for this item would fire the moment the learner presses Enter to run `vim vim-notes.md` at the shell, before the file is even open. With it, the hint is suppressed until the learner has the file open and is actually working on the step.

Conditions may be combined. For example, `{ "fileOpen": "computer-mouse.md", "register": { "equals": "..." } }` waits until the learner has copied the required text and returned to the target file before evaluating a paste-result check.

The `absent` condition is useful in puzzle lessons to gate the item on placeholder removal:

```json
{
  "label": "Enter the correct answer.",
  "hint": "You should replace the placeholder with your answer.",
  "attemptsBeforeHint": 3,
  "targetLine": "Answer:",
  "evaluateWhen": { "fileChanged": "study.md", "absent": "[answer goes here]" },
  "test": { "file": "study.md", "contains": ["Answer: correct"] }
}
```

This item becomes eligible only after the learner has edited `study.md` and removed the placeholder text `[answer goes here]`.

Use `files` instead of `file` when one checklist item should require the same content predicates to hold in multiple files. Each file is checked against its matching `# --expected--` block.

**Test fields — session predicates (what the learner did).** Checked against a record of past actions, so they're permanent. Once true, the item stays ticked even if the learner undoes the action.

| Field           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `command`       | A specific keystroke or command was entered at some point. Accepts a plain string (`"G"`) or a command-matcher object (`{ "command": "G", "fromMode": "normal", "commandAt": [3, null] }`). Use the object form when you need `fromMode` — the loader rejects `fromMode` as a flat test field. This is an existence check, not a count, unless `count` is set. Ignores characters typed in insert mode, so typing "A" never satisfies the normal-mode `A`. |
| `anyOfCommands` | A list of command matchers. The item ticks when any one matcher is satisfied. Use this for several equally-correct keystrokes with no end state that distinguishes them. Mutually exclusive with `command`; minimum two entries.                                                                                                                                                                                                                            |
| `exact`         | Modifier for one command matcher. Flat alongside a string `command`, inside the command-matcher object, or nested inside an `anyOfCommands` entry. Never flat alongside `anyOfCommands`.                                                                                                                                                                                                                                                                   |
| `count`         | Modifier for one command matcher. Flat alongside a string `command`, inside the command-matcher object, or nested inside an `anyOfCommands` entry. Never flat alongside `anyOfCommands`.                                                                                                                                                                                                                                                                   |
| `commandAt`     | Modifier for one command matcher. Requires the command to have been issued while the cursor was at this `[line, column]` position (1-based, `null` for unconstrained axis). The check is atomic: the history entry must match both the command and the position, so two `yy` steps on different lines do not cross-satisfy each other. When `command` is a string, `commandAt` may be flat on the test object. When `command` is an object, `commandAt` must be inside the object — a flat `commandAt` is not applied to an object-form matcher. Never flat alongside `anyOfCommands`. |
| `fromMode`      | Modifier for one command matcher. Requires the command to have been issued from the named Vim mode. **Must be inside the command-matcher object** — the loader rejects it as a flat test field. Use it when a key's meaning depends on the mode it leaves: `{ "command": { "command": "Esc", "fromMode": "visual" } }`.                                                                                                                                     |
| `open`          | A specific file is the active buffer. Any route there counts.                                                                                                                                                                                                                                                                                                                                                                                              |
| `cursorAt`      | Position(s) the cursor must reach, as `[line, column]` or `[[l,c], ...]`. Use `null` in either slot to leave that axis unconstrained (`[3, null]` means any column on line 3). An array of positions passes when every position has been visited. The label may use `{count}` and `{total}` for live progress.                                                                                                                                             |

**Test fields — state predicates (what is true now).** Checked on every keystroke and always re-evaluated. An edit can be undone or Vim can reopen, so the item ticks and un-ticks as the buffer changes.

| Field                                 | Meaning                                                                                                                                                                                                                                                                                                          |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file`                                | The file the other state fields read. **Required by all of them but `quit`** — there is no default, not even `open`.                                                                                                                                                                                             |
| `newFile`                             | `true`: `file` names a path the learner creates during the lesson, so it is not seeded in `# --files--`. Only with `file`.                                                                                                                                                                                       |
| `equals`                              | File's exact full contents, `\n` between lines.                                                                                                                                                                                                                                                                  |
| `notEquals`                           | File's full contents must differ from this exact text. Useful for lessons that ask for any change rather than one specific end state.                                                                                                                                                                            |
| `equalsExpected`                      | `true`: same as `equals`, with the text taken from this file's `# --expected--` block. Only `true`; never with `equals`.                                                                                                                                                                                         |
| `equalsExpectedNormalizingWhitespace` | `true`: like `equalsExpected`, but blank (empty or whitespace-only) lines are dropped and trailing whitespace is trimmed on both sides before comparing. Indentation and inter-word spacing stay significant. At most one of `equals`/`equalsExpected`/this.                                                     |
| `contains`                            | File satisfies every needle. Each is a plain substring, or a `/pattern/flags` literal matched as a regex over the whole joined file text — use the regex form to assert order across lines ("X after Y"), which per-line `line.matches` cannot.                                                                  |
| `absent`                              | File satisfies none of the needles, in the same substring-or-`/regex/` form as `contains`.                                                                                                                                                                                                                       |
| `occurrences`                         | Each `{ "needle": "...", "count": N }` requires exactly `N` matches. Plain needles count substrings; `{ "exact": true }` counts exact line matches; `/pattern/flags` needles count regex matches. `exact` cannot be combined with regex needles.                                                                 |
| `line`                                | Predicate over one line: `{ "number": N, "equals": "...", "contains": "...", "matches": "<regex>" }`. Past-end number fails.                                                                                                                                                                                     |
| `blank`                               | `true`: file is empty or whitespace-only. `false`: file has non-whitespace content. Prefer over `equals: ""` when the lesson empties a file — a stray space or blank line still passes.                                                                                                                          |
| `matchAgainstSaved`                   | `true`: point `equals`/`notEquals`/`contains`/`absent`/`occurrences`/`line`/`blank` at the last written copy, not the live buffer, so the item moves only on `:w`. See below.                                                                                                                                    |
| `saved`                               | `true`: file written and no unsaved changes. A pristine untouched file fails — clean is not the same as saved.                                                                                                                                                                                                   |
| `quit`                                | `true`: Vim has been left for the terminal. Reopening Vim makes the item fail again. A state field needing no `file`.                                                                                                                                                                                            |
| `lineNumbers`                         | `true`/`false`: whether the line-number gutter is on now. Live, so it reads the end state — use it for "hide the numbers again", not `{ command: ":set nonumber" }`. Needs no `file`.                                                                                                                            |
| `register`                            | A live, non-latching predicate over the unnamed register's text. Mirrors `line` semantics with optional `equals`, `contains`, and `matches` fields, which combine with AND. Needs no `file`.                                                                                                                     |
| `quickfix`                            | A live, non-latching predicate over the quickfix list built by the last `:vimgrep`/`:grep`. Fails until the first such run. Accepts `count` (exact entry count), `minCount` (at least N entries), and/or `contains` (every entry's matched line must contain the text), which combine with AND. Needs no `file`. |

An item latches only when every field it _asserts_ is a session predicate; one state predicate makes the whole item live. `file`, `newFile`, `exact`, `count`, and `matchAgainstSaved` assert nothing on their own and never decide.

**No `dirty` field exists.** Use:

| the question                | the test                                                  |
| --------------------------- | --------------------------------------------------------- |
| Did they edit it correctly? | `equals` / `contains` / `absent` / `occurrences` / `line` |
| Did they empty it?          | `blank: true`                                             |
| Did they save it?           | `saved: true`                                             |
| Did they leave it alone?    | `equals: "<the seeded text>"`                             |

Fields combine with AND across both families.

Every state predicate but `quit` asks about one file, so a test using one must name which file. There is no lesson-wide default, and `config.open` is deliberately not one. A missing `file` silently points the assertion at the wrong path, invisible in review and surfacing only as a lesson that cannot finish. The loader rejects this by name. `quit` is about the session rather than a file and takes no `file` at all.

## Files the learner creates

`:e <name>` on a path that doesn't exist opens an empty buffer under that name. `:w` writes it. The app's virtual filesystem holds it exactly as Vim would. A test can assert on such a file, but it has to say so. The loader otherwise reads a path missing from `# --files--` as a typo and throws.

```json
{
  "label": "Create `notes.md`, add the line, and save it.",
  "test": { "file": "notes.md", "newFile": true, "equals": "...", "saved": true }
}
```

`newFile` only accompanies a `file`, never a seeded path. Every item naming that path must agree. The loader rejects all three mistakes. `open` still resolves against seeded files only. A lesson cannot start open on a file that doesn't exist.

A created file is a full member of the lesson's namespace otherwise. It can own an `# --expected--` block and be read with `equalsExpected` exactly like a seeded one.

Fold the content and the save into one item, as above. Split across two, and a learner who creates the file, types the wrong text, and saves watches the save item tick while the content item stays open. That reads as credit for wrong work. Use two only when the lesson wants the save as its own beat.

There is no "the file exists" test, by design. Opening the path creates it. Such an item would tick before a character is typed and could never untick again.

## Saving is per file

`saved` asks about one file. `:w` and `:wq` write the file currently open and no other. The engine has no `:wa`, so a lab with a `saved` item per file needs one write per file.

`:wq` also leaves Vim for the shell. A learner who uses it partway through a multi-file lab has to run `vim` again to reach the next file. Point instructions or hints at `:w` then `:e <next file>`. Leave `:wq` for the last one.

## Reading the saved copy (`matchAgainstSaved`)

Content predicates (`equals`, `contains`, `matches`, `absent`, `occurrences`, `line`, `blank`) default to the live buffer. Adding `matchAgainstSaved: true` redirects them at the last written copy, so the checkmark moves only on `:w`, not as the learner types.

Buffer-level checks give immediate feedback while the learner edits. Use them on command-paired items (`command` + `blank`, `command` + `absent`, etc.) so the learner sees the result of each step right away. Use `matchAgainstSaved` on the final content-equality check that gates lesson completion.

```json
{
  "label": "Fix the spelling and save.",
  "test": { "file": "words.txt", "matchAgainstSaved": true, "equals": "color\nfavorite" }
}
```

`matchAgainstSaved` needs a `file` and at least one content predicate to redirect; the loader rejects it otherwise. It never touches `saved`, which asks about write state rather than contents.

**Cross-item rule: saved files must have a content check.** When a checklist requires saving a file (`saved: true`), it must also include an `equals`/`equalsExpected`/`equalsExpectedNormalizingWhitespace`/`matches` check with `matchAgainstSaved: true` for that file. The loader enforces this at the checklist level. Without it, a learner could save the untouched seed and pass all checks.

**Seed-matching predicates need `saved: true`.** A seeded file's saved copy starts as its seed text. A `matchAgainstSaved` predicate that already holds against the seed would tick before the learner touches anything. The loader rejects that unless the test also asserts `saved: true`.

One honest consequence to keep in mind while authoring. The item reads the disk copy, so a learner can save the correct text and then wreck the buffer without un-ticking it. That's the intended framing of "you saved the right thing", not a gap.

## `equals` vs. `equalsExpected`

Both are the same assertion, differing only in where the text is authored. Use `equalsExpected` when the target text runs longer than a line. A `# --expected--` block stays readable and reviewable, while an inline `equals` becomes a single `\n`-escaped JSON string. Keep `equals` inline for short one-liners. Prefer a narrower field (`line`, `contains`, `absent`) when the lesson doesn't constrain the entire file.

### `matches`

Use `matches` for an inline `/pattern/flags` regular expression over the entire file. Unlike `contains`, which searches for a needle anywhere in the file, `matches` communicates that the pattern should normally be anchored with `^` and `$`. Use character classes or spacing expressions to relax only the intended part of the file.

```json
{
  "file": "dna.md",
  "matches": "/^Header\\n[Tt][ \\t]*[Aa][ \\t]*[Cc]$/",
  "matchAgainstSaved": true
}
```

### `equalsExpected` vs. `equalsExpectedNormalizingWhitespace`

Both read the same `# --expected--` block. They differ only in how strict the comparison is.

- **`equalsExpected`** Exact, byte for byte. Every blank line and trailing space must match. Use this for a file the learner must **leave untouched** (a multi-file lab where one file is off-limits, even to a stray space) or a lesson where **the exact layout is the point**.
- **`equalsExpectedNormalizingWhitespace`** Drops blank lines and trims trailing whitespace on both sides before comparing. Blank-line placement between sections is the learner's own business. Indentation and spacing between words stay significant, so joining two paragraphs onto one line or reindenting still fails. Use this for an **edit/rearrange gate** where content and order matter, not spacing. Don't fail a learner for a missing or extra blank line between sections.

Author the expected block the same way for both — a full, readable file. The choice of spelling, not a flag, decides whether whitespace is graded, and a test may set **at most one** of `equals` / `equalsExpected` / `equalsExpectedNormalizingWhitespace`.

Do **not** author blank-line-position checklist items (`{ "line": { "number": N, "matches": "^\\s*$" } }`) to force section spacing. Those pin absolute line numbers and turn an editorial detail into a pass/fail gate the learner cannot diagnose. Let `equalsExpectedNormalizingWhitespace` ignore the spacing instead.

Which block a test reads is decided by the file it reads — always `test.file` — so a multi-file lab gives each file its own item and its own block:

```json
"checklist": [
  { "label": "Fix `cursor-origin.md`.", "test": { "file": "cursor-origin.md", "equalsExpected": true } },
  { "label": "Fix `cursor-shapes.md`.", "test": { "file": "cursor-shapes.md", "equalsExpected": true } }
]
```

The loader rejects a mismatch between the two sides rather than validating against nothing, so a typo in either place fails the build and the test suite:

- `equalsExpected` on a test that names no `file`, or on a file with no block of that name.
- A `# --expected--` block no checklist test reads.
- A `# --expected--` block naming a file `# --files--` never seeds and no test declares with `newFile`.
- `equals` and `equalsExpected` on the same test, or `equalsExpected: false`.
- Two items asserting different full contents for one file, which could never both hold.

## Command matching

A command matcher is:

```json
"<command>"
```

or:

```json
{ "command": "<command>", "exact": true, "count": 7, "commandAt": [3, null], "fromMode": "normal" }
```

A bare string is sugar for `{ "command": "..." }`.

Singular `command` can be either a plain string (with `exact`, `count`, and `commandAt` flat on the test object) or an object (with all modifiers inside it). Use the object form when you need `fromMode` — the loader rejects `fromMode` as a flat test field:

```json
{ "command": "G", "count": 7 }
```

```json
{ "command": { "command": "~", "fromMode": "normal", "commandAt": [11, 3] } }
```

**Important:** when `command` is an object, flat modifiers on the test object are not applied to it. `commandAt` flat on the test only works when `command` is a string. Put all modifiers inside the object when using the object form.

`anyOfCommands` is a list of command matchers and passes when any entry matches:

```json
{ "anyOfCommands": [{ "command": "G", "count": 7 }, "gg"] }
```

The item ticks on `7G` or `gg`. A bare `G` satisfies neither. Modifiers live on entries because a top-level `count` could not target only one alternative.

Matching behavior itself is unchanged. `:e` matches `:e notes.md`, `vim` matches `vim notes.md`, `:%s` matches `:%s/a/b/g`. It never works in reverse: `vim notes.md` is not satisfied by bare `vim`. It never reaches a longer verb: `:w` is never satisfied by `:wq`.

Use `exact` when the lesson teaches one spelling among several that do the same thing (for example, `:set nonumber` exact so `:set nonu` does not complete it). Counts stay separate unless specified (`G` matches `7G` until a matcher requires `count`). `Esc` matches the engine's `Escape` token.

Use `commandAt` when the lesson needs to verify the command was issued at a specific cursor position. The check is atomic: the same history entry must match both the command and the position. Without `commandAt`, `command` and `cursorAt` are independent session predicates that can be satisfied by different keystrokes, so a `yy` on line 1 plus a cursor visit to line 3 would satisfy both. `commandAt` prevents that: `{ "command": "yy", "commandAt": [3, null] }` requires `yy` to have been pressed while the cursor was on line 3. This scales to any number of same-command items on different lines.

Use `fromMode` when a key's behavior depends on which mode issued it (for example, `~` in visual mode acts on a selection; in normal mode it toggles one character). Because `fromMode` must live inside the command object, pair it with `commandAt` inside the same object when both constraints apply.

`anyOfCommands` is for session-predicate items with no distinguishing end state. Save, quit, and edit alternatives should keep using `saved`, `quit`, and content predicates.

`:e! <path>` is recorded as a distinct verb from `:e`. A `command: ":e"` item is not satisfied by `:e! notes.md`. A lesson whose task is `:e <path>` should expect the learner to `:w` first if the previous step left the buffer dirty. Say so in the instructions or hint.

**When `command` matching requires Enter.** A `command` test checks only whether a matching action exists in history. It has no knowledge of Enter itself. Which path produced the action decides:

- **Ex commands** (`:w`, `:e <path>`, `:wq`, etc.) record their action on Enter. A `command: ":w"` item stays open until the learner presses Enter after typing `:w`.
- **Single-key normal-mode commands** (`i`, `x`, `dd`, `G`, `gg`, etc.) record on keypress — no Enter required.
- **Shell commands** (`vim`, `vim <file>`) record on Enter.
- **Netrw Enter** records immediately, like a single-key command.
- **Insert-mode Enter** records `{ type: 'insert', command: 'Enter' }`, distinct from any command-line path, and never matches a `command` test targeting a normal-mode key.

## `allowedCommands` gating

Restricts taught Vim commands only. Always allowed without listing:

- Arrow keys in normal mode and insert mode (unless explicitly denied via `disallowedCommands`).
- Backspace and Enter in insert mode, and typing any character.

The filter gates the resolved command, not the leading key. It matches exactly as a `command` test does. `[":w"]` permits `:w` and `:w foo` but not `:wq`. A single key permits only itself. A bare `":"` or `"/"` entry is a family wildcard for any ex command or any search. Entering the command line or search prompt is always permitted. The command typed there is judged on Enter.

## `disallowedCommands`

Everything runs except the listed commands, matched the same way. `[":q"]` forbids only `:q` and leaves `:w`, `:wq`, and everything else working.

Arrow keys are the one class of command that `allowedCommands` never restricts but `disallowedCommands` can block. Deny them individually (`"ArrowUp"`, `"ArrowDown"`, `"ArrowLeft"`, `"ArrowRight"`) or as a group (`"@arrows"`). A denied arrow key is blocked in both normal and insert mode.

With both lists present, `allowedCommands` restricts first. `disallowedCommands` subtracts from what remains.

Neither list can force one specific spelling when the learner could reach the same state another way. Use the checklist: a `command` matcher plus a state predicate. Don't use the input filter for this.

## `commandLimits`

Caps how many times a command may run, layered on top of the two lists. A capped command need not be allow-listed; a cap only further restricts.

Keys are matched exactly as `allowedCommands` entries are. Values are a positive integer (invocation cap) or `{ "times": N, "maxCount": N }`:

- **`times`** — maximum number of invocations.
- **`maxCount`** — maximum count prefix on any single invocation.

An over-cap command is refused with a `filtered` action and a status-line message ("limit reached" or "count too high"). This counts as an attempt and reveals the current hint.

Two things to know:

- **A cap counts invocations, not units.** `3dd` is one invocation, so `{ "dd": 3 }` still lets a learner delete far more than three lines via counts. Pair with `maxCount` (`{ "dd": { "times": 3, "maxCount": 1 } }`) when a large single sweep defeats a "be surgical" lesson.
- **No undo refund.** A press spent against a cap stays spent through `u`. A learner who miscounts must use Reset.

`@`-group keys are rejected in `commandLimits` at load — a cap is per command, not per group.

## `highlightVisited`

When `true`, every buffer cell the cursor occupies is rendered with a green "visited" highlight. The trail persists for the lifetime of the lesson (reset clears it). Useful for letter-tracing exercises where the learner navigates a shape and needs to see which positions remain. The starting cursor position is highlighted on seed.

## `decorativeRanges`

Marks ranges of lines in seed files as decorative ASCII art for screen readers.
Each entry names a file and a 1-based inclusive line range. Without a
`description`, the lines are hidden from the accessibility tree
(`aria-hidden="true"`). With a `description`, consecutive lines in the range are
wrapped in a single `role="img"` container and announced as a described image.

When the learner's edits can shift or delete the drawing, add an `anchor` needle
so the range is applied only while the anchor matches the buffer line at the
range's start position. Without an anchor the range always applies (suitable for
persistent drawings that the learner never moves).

```json
{
  "decorativeRanges": [
    {
      "file": "art.txt",
      "lines": [1, 3],
      "description": "A small cat sitting with a cup of tea",
      "anchor": "/  \\//"
    },
    { "file": "art.txt", "lines": [5, 6] }
  ]
}
```

Rules:

- The `file` must match a seeded file in `# --files--`.
- `lines` is a two-element array `[start, end]` of 1-based integers where
  `start <= end`, and `end` must not exceed the file's line count.
- `description` is optional. When provided, it must be a non-empty string.
  Write it as alt text: describe what the image shows, not how it is constructed.
- `anchor` is optional. A needle (plain substring or `/pattern/flags` regex)
  tested against every buffer line within the range on each render. The range
  stays active while at least one line matches. When none match (the drawing was
  fully deleted or shifted away), the range is silently skipped. Use it for
  drawings the learner will delete or rearrange.
- Lines the learner must edit should NOT appear in a decorative range. Leave
  them as normal content listitems so screen readers can navigate them.

The loader validates ranges against seed content at load time.

## Dynamic labels with `{count}` and `{total}`

When `cursorAt` holds an array of positions, the checklist label may include `{count}` and `{total}` placeholders. `{total}` is the number of positions in the array (static), and `{count}` is how many of those positions the learner has visited so far (monotonically increasing).

```json
{
  "label": "Trace the V ({count} of {total})",
  "test": {
    "cursorAt": [
      [2, 1],
      [3, 2],
      [4, 3],
      [5, 4],
      [4, 5],
      [3, 6],
      [2, 7]
    ]
  }
}
```

The label renders as "Trace the V (0 of 7)" at seed and updates as positions are visited, reaching "Trace the V (7 of 7)" when the item completes. Positions may be visited in any order. The placeholders have no effect on single-position `cursorAt` tests.

Count-only changes (3 of 7 to 4 of 7) update the label visually without triggering a screen-reader announcement. The completion announcement fires when the item's status transitions to `completed`.

## Command group aliases

`allowedCommands` and `disallowedCommands` accept `@`-prefixed group names from `src/curriculum/commandGroups.ts` (for example `"@navigation"`, `"@arrows"`), expanded to their member commands at load. Mix freely: `["@navigation", "x"]`. An unknown alias throws at load.

## Seed continuity

Every interactive lesson carries its own complete `# --files--` block. Nothing persists at runtime. A module's file appears to progress across lessons because each lesson's seed is authored as the previous lesson's end state. One fact is written twice deliberately. The integrity suite asserts that consecutive lessons in a module naming the same path agree on its text. The rule is scoped per module and per path. A lab introducing its own file is unconstrained.
